# Разработка и отладка

## Структура репозитория

```text
ModulePrometheus/
├── module.json                  # манифест модуля
├── App/                         # MVC веб-интерфейса
│   ├── Module.php               # обязателен: без него роутер не регистрирует маршрут
│   ├── Controllers/
│   ├── Forms/
│   └── Views/
├── Lib/
│   ├── WorkerPrometheusExporter.php
│   ├── MetricsCollector.php     # фасадка
│   ├── Collectors/              # System, Asterisk, Telemetry, CallStats,
│   │                            # Infrastructure, MetricsWriter, CollectorRegistry
│   ├── StatsCache.php           # cron-коллектор CDR
│   ├── ApiHelper.php
│   ├── PrometheusMain.php       # настройки и жизненный цикл
│   ├── PrometheusConf.php       # хуки MikoPBX
│   └── RestAPI/Status/          # status:getStatus, status:testConnection,
│                                # status:getExporterInfo
├── Models/                      # m_ModulePrometheus (аннотации колонок)
├── Messages/                    # en.php, ru.php, languages.php
├── Setup/                       # PbxExtensionSetup: unInstallFiles
├── bin/                         # обёртки запуска и cron-скрипты (ТОЛЬКО LF!)
├── public/assets/               # JS/CSS/логотип; src/ — исходники, корень — отдаваемая копия
├── docs/                        # этот Obsidian-vault
├── examples/                    # alerts.yml с готовыми правилами
└── db/, agi-bin/                # каталоги-заглушки платформы
```

> [!warning] `Messages/*.php` обязаны начинаться с `return [`
> Core грузит переводы через `$langArr = require $path;` и проверяет
> `is_array($langArr)`. Файл без `return` вернёт `1`, переводы молча
> пропадут, а в интерфейсе появятся сырые ключи вида `modpma_ServiceStatus`.

> [!warning] `App/Module.php` обязателен
> `PbxExtensionUtils::registerEnabledModulesInRouter()` добавляет маршрут
> модуля только если файл существует. Без него модуль устанавливается,
> но его страница отдаёт 404.

> [!danger] Вольт читает переменные представления как обычные PHP-переменные
> `{{ settings.listenAddress }}` **не работает**: точечная запись не
> достаёт элемент массива, и в шаблон попадает пустое значение. Так
> страница настроек в 1.3.x показывала пустые поля при работающем
> экспортёре, а сохранение затирало настройки.
>
> Правильно — передавать отдельные переменные:
> ```php
> $this->view->listenAddress = $settings->listenAddress;
> ```
> ```volt
> <input type="text" name="listenAddress" value="{{ listenAddress }}">
> ```
> В ядре админки так же: ни один view не использует `{{ x.y }}`.

## Конвенции

> [!warning] Жёсткие требования платформы
> - Скрипты `bin/*.sh` — **только LF** (CRLF ломает busybox sh).
> - Shell-код исполняется busybox: без bash-измов, явные апплеты
>   (`/bin/busybox cat` и т. п.).
> - PHP 8.4, Phalcon 5, неймспейс `Modules\ModulePrometheus\…`.
> - Каждый PHP-класс CLI получает DI через `require_once 'Globals.php'`.

## Ручной запуск и остановка

На АТС по SSH:

```sh
# Каталог модуля (продакшен-путь)
MOD=/storage/usbdisk1/mikopbx/custom_modules/ModulePrometheus

# Запустить экспортер вручную (в foreground — видно ошибки)
php -f $MOD/Lib/WorkerPrometheusExporter.php start

# Остановить (воркер ставит заголовок процесса ModulePrometheusExporter)
kill $(busybox ps | grep '[M]odulePrometheusExporter' | busybox awk '{print $1}')

# Проверить ответ
curl -s http://127.0.0.1:9713/metrics | head
curl -s http://127.0.0.1:9713/-/healthy
```

> [!tip] Отладка с токеном
> ```sh
> curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:9713/metrics
> ```
> Без токена при включённой авторизации придёт `401 unauthorized`.

## Отладка коллектора кэша

```sh
MOD=/storage/usbdisk1/mikopbx/custom_modules/ModulePrometheus

# Прогнать сборщик статистики вручную (нужен запущенный PBX)
php -f $MOD/Lib/StatsCache.php

# Что получилось
ls -la /storage/usbdisk1/mikopbx/tmp/ModulePrometheus/
cat /storage/usbdisk1/mikopbx/tmp/ModulePrometheus/last_update
```

## Логи

Модуль пишет в syslog MikoPBX с тегами `ModulePrometheus*`
(например, `ModulePrometheusExporter_BIND_ERROR`). Смотрите системный
журнал PBX (`/var/log/messages` или раздел диагностики интерфейса).

## Проверка синтаксиса при разработке

```sh
php -l Lib/MetricsCollector.php       # для каждого изменённого файла
sh -n bin/prometheus-safe-script.sh   # проверка shell-скриптов
```

## Сборка архива

```powershell
powershell -ExecutionPolicy Bypass -File .\build-module.ps1
```

Скрипт кладёт содержимое модуля в корень архива и проверяет структуру
тем же способом, которым проверяет MikoPBX. **Не используйте
`Compress-Archive -Path "ModulePrometheus"`** — получится zip с лишним
уровнем вложенности, и установка упадёт на `module.json`.

## Как добавить новую метрику

1. Выберите или создайте коллектор в `Lib/Collectors/`.
2. Внутри опишите семейство:

```php
$w->metric(
    'mikopbx_something_total',
    'What it counts',
    'counter',
    [[['trunk' => 'tr1'], 42]]
);
```

   `MetricsWriter` сам поставит `HELP`/`TYPE`, экранирует метки и
   пропустит пустое семейство.
3. Если источник может упасть — бросьте `RuntimeException`. Тогда
   `mikopbx_exporter_collector_success` станет `0`. Внутри одного
   коллектора необязательные блоки оборачивайте в `optional()`, иначе
   одна ошибка убьёт все метрики после неё — так в 1.3.0 потерялось
   12 семейств из-за несуществующей константы `Directories::CORE_DB_DIR`.
4. Добавьте строку в [[Справочник метрик]] и правило
   в [[Алертинг и Grafana]].

## Проверка после обновления на живой АТС

```bash
# сколько семейств отдаётся сейчас
curl -s http://<АТС>:9713/metrics | grep -c '^# HELP mikopbx_'

# все ли сборщики живы
curl -s http://<АТС>:9713/metrics | grep collector_success

# есть ли падающий сборщик (503 = да)
curl -s -o /dev/null -w '%{http_code}\n' http://<АТС>:9713/-/ready

# какие необязательные блоки упали
curl -s http://<АТС>:9713/metrics | grep block_error_info

# какие блоки не отдали данных и почему
curl -s http://<АТС>:9713/metrics | grep block_absent_reason

# счётчики процесса экспортёра
curl -s http://<АТС>:9713/-/info
```

> [!warning] Проверять по списку живых метрик, а не по непустому ответу
> Запрос к удалённой метрике ещё около часа отдаёт данные из истории TSDB
> и выглядит рабочим. Единственный честный признак — отсутствие семейства
> в свежем ответе экспортёра.

1. Соберите значение в `MetricsCollector` (секция по источнику).
2. Опишите метрику через `$this->metric(имя, HELP, тип, samples)` —
   HELP/TYPE и экранирование labels сделает helper.
3. Если источник может падать — он уже изолирован в `runCollector`
   (метрика `collector_success` покажет сбой).
4. Добавьте строку в [[Справочник метрик]] и (по желанию) алерт
   в [[Алертинг и Grafana]].
